# gear-1: Vault async flows send no reply deposit and treat a reply timeout as "the transfer did not happen", so a lost or late token reply makes the compensation double-pay (redeem/claim/collect_fees) or strand tokens (deposit/fund_rewards)

**Location**
- `/Users/adityakrx/liquid-stake/programs/vault/app/src/lib.rs:716` and `:726` (`.with_gas_limit(TOKEN_CALL_GAS)` only; no `.with_reply_deposit(..)`)
- `/Users/adityakrx/liquid-stake/programs/vault/app/src/lib.rs:720`, `:730` (`Err(e) => Err(VaultError::TokenCall(..))` folds `Error::Timeout` into the same arm as a real error reply)
- `/Users/adityakrx/liquid-stake/programs/vault/app/src/lib.rs:772-781` (`redeem`: any `Err` -> `revert_redeem` + re-mint event), `:810-818` (`claim`: `restore_unbond`), `:907-915` (`collect_fees`: `restore_fees`), `:747` and `:834` (`deposit` / `fund_rewards`: `?` returns before `settle_deposit` / `fund`)
- `/Users/adityakrx/liquid-stake/programs/vault/app/src/lib.rs:45-46` (`TOKEN_CALL_GAS = 6_000_000_000`, "measured ~1.5B")

**Bug class** Async execution model: reply handling gas not provisioned (missing `gr_reply_deposit`), and timeout conflated with failure (distributed-transaction compensation on an unknown outcome).

**Severity** Medium

**Description**

How the reply is paid for. The vault sends the token call through the Sails gstd client. With no `with_reply_deposit`, the client passes `reply_deposit = 0`:
`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/sails-rs-1.0.1/src/client/gstd_env.rs:141` (`let reply_deposit = params.reply_deposit.unwrap_or_default();`) -> `gstd::msg::send_bytes_with_gas_for_reply(dest, payload, gas_limit, value, reply_deposit)`, and gstd only calls `exec::reply_deposit` when the deposit is non-zero (`gstd-codegen-1.10.0/src/lib.rs:402-405`). The reference `references/gear-gstd-api-and-syscalls.md` lists `exec::reply_deposit` / `gr_reply_deposit` as the API that "Allocate[s] reply deposit for `handle_reply`", and `references/gear-messaging-and-replies.md` states "A reply hook needs non-zero reply deposit to register."

Without a deposit, the token's reply (`reply_bytes` -> `ReplyPacket` with `gas_limit: None`) is attached to the gas node of the *token's* message: `gtest-1.10.0/src/manager/journal.rs:173-176` `(None, None) => self.gas_tree.split(dispatch.is_reply(), message_id, dispatch.id())`, i.e. an `UnspecifiedLocal` node that has no value of its own and draws on its parent (`gear-common-1.10.0/src/gas_provider/node.rs:213-218, 342`). So the vault's `handle_reply` entrypoint (generated by Sails, `sails-macros-core-1.0.1/src/program/mod.rs:373-383`, which runs `gstd::handle_reply_with_hook()` -> `signals().record_reply()` -> `exec::wake(original_msg)` at `gstd-1.10.0/src/async_runtime/signals.rs:68-86`) is paid from whatever the token left of the 6B `TOKEN_CALL_GAS`, not from the vault message's gas and not from anything the vault controls. The continuation after the wake (settle/compensate) is paid from the original message's gas; the `GAS_ONE_CALL` guard covers only that part.

What happens when `handle_reply` cannot run (not enough leftover gas, or the reply is simply late). `record_reply` never executes, so the waiting vault message is not woken by the reply. `wait_up_to` expires after `Config::wait_up_to() = 100` blocks (`gstd-1.10.0/src/config.rs:73`; the Sails client calls `message_future.up_to(params.wait_up_to)` at `gstd_env.rs:155`, `None` -> the default). The runtime wakes the message, `MessageFuture::poll` sees the timeout and returns `Err(Error::Timeout(expected, now))` (`gstd-1.10.0/src/msg/async.rs:41-46`). The vault maps that to `TokenCall(..)` (`lib.rs:720/730`) and runs the compensation branch even though the token has already applied the transfer:

- `redeem`: shares were burned and `holdings -= net` pre-await, the token has already moved `net` to the owner, and `revert_redeem` now re-mints the shares and adds `net` back to `holdings` (`lib.rs:413-417`). The owner keeps the tokens *and* the shares; `holdings` overstates what the vault holds by `net`, so the rate is inflated for everyone until the next honest redeem hits `InsufficientReserve`.
- `claim` / `collect_fees`: same shape via `restore_unbond` / `restore_fees`: paid out once, then restored for a second payout.
- `deposit` / `fund_rewards`: the `?` at `lib.rs:747` / `:834` returns `Err` before `settle_deposit` / `fund`; the tokens have already been pulled by `transfer_from` and are now in the vault's token balance but not in `holdings`. There is no sweep or reconciliation path, so they are unrecoverable.

The reference calls this exact pattern out: "Treat reply, timeout, and late hook execution as distinct states" and "A timed-out future does not guarantee the reply hook never runs later if the reply eventually arrives" (`references/gear-messaging-and-replies.md`), and lists "Timeout followed by later side effects" as a failure signature (`references/gear-gas-reservations-and-waitlist.md`). A late reply after the timeout is harmless to gstd itself (`record_reply` finds the stale signal, `exec::wake` targets a message that is no longer waiting, the runtime logs "Failed to wake unknown message", `gtest-1.10.0/src/manager/journal.rs:206-247`), but the vault has already compensated.

**Trigger**
1. The token's `transfer`/`transfer_from` consumes enough of the 6B that the vault's `handle_reply` (module instantiation + loading the pages holding gstd's `SIGNALS`/`LOCKS` maps + `gr_wake`) cannot complete. The token's per-call cost grows with its `balances`/`last_claim` BTreeMaps (more pages touched); runtime weight changes on upgrades move both numbers. Nothing in the vault pins the leftover.
2. Independently of gas: the token reply is delayed more than 100 blocks (queue congestion or the token program being paused/reinstrumented), or the reply is processed after the timeout for any other reason.
3. When the token traps with `RanOutOfGas`, the system error reply also has `gas_limit: None` (`gear-core-1.10.0/src/message/reply.rs:211-218`) on a node with ~0 gas, so the vault cannot process it either; the message sits in the waitlist for 100 blocks (~5 min on Vara) before the (in that case correct) compensation runs.

**Impact** State/asset divergence in the vault's favour or against it depending on the flow: double payout on redeem/claim/collect_fees, permanent loss of pulled tokens on deposit/fund_rewards, and an inflated `holdings` after a double payout. No attacker lever is needed; it is a reliability boundary that the current gas constants happen to sit inside.

**Confidence** High on the mechanism (all steps are in the vendored 1.10 sources and the vault code). Medium on on-chain likelihood: the actual gas the vault's `handle_reply` needs versus the token's leftover of 6B was not measured here (UNVERIFIED), and the deploy smoke run reported in the README implies it currently fits.

**Suggested fix**
1. Provision the reply explicitly: `.with_gas_limit(TOKEN_CALL_GAS).with_reply_deposit(REPLY_GAS)` on every token call, with `REPLY_GAS` measured for the vault's `handle_reply` (a few billion), and raise `GAS_ONE_CALL` by the same amount so the deposit is covered by the caller's message.
2. Distinguish outcomes instead of compensating on any `Err`: `Ok(Ok(true))` -> settle; `Ok(Err(_))` / `Ok(Ok(false))` / `Err(ErrorReply(..))` -> compensate; `Err(Timeout(..))` -> do *not* compensate. Record the in-flight operation (owner, amount, token message id) in a `pending` map and expose an admin/keeper `resolve_pending(id)` that queries the token balance (or receives the late reply through a `handle_reply` hook with a deposit) before releasing or restoring. The `awesome-sails-msg-tracker` pattern in `references/gear-sails-production-patterns.md` is the reference shape.
3. Add a bounded admin reconciliation for stranded deposits: `sweep_untracked()` that reads `token.balance_of(vault)` and credits `holdings` (or the affected depositor) with the excess over `holdings`.
