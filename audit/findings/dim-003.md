# DIM-003: Vault minimum deposit and receipt `decimals` assume a 6-decimal underlying but are never checked against it

**Severity:** LOW
**Type:** decimals_assumption (Trap 5 family: a base-unit constant whose token meaning depends on an unverified `decimals()`)
**Location:** `/Users/adityakrx/liquid-stake/programs/vault/app/src/lib.rs:37-38,208,381,575,1009`
**Related:** `/Users/adityakrx/liquid-stake/scripts/deploy.ts:128,134` (passes `6` to both the token and the vault)

## Code

```rust
/// Smallest deposit in base units so share rounding can never produce zero.
pub const MIN_DEPOSIT: u64 = 1_000;                     // D?{asset}: 0.001 tokens only if the underlying is D6
...
pub fn new(underlying: ActorId, name: String, symbol: String, decimals: u8, ...) -> Self   // `decimals` is caller-supplied
...
if assets < U256::from(MIN_DEPOSIT) { return Err(VaultError::BelowMinimum { min: U256::from(MIN_DEPOSIT) }); }
```

## Analysis

The vault is written as generic over "one underlying VFT" (`underlying: ActorId`), but two quantities
that should be functions of the underlying's precision are fixed or free-form:

1. `MIN_DEPOSIT = 1_000` is a base-unit literal. Its meaning in tokens is `1e3 / 10^decimals`:
   0.001 USDC for the demo tokens (D6), 1e-15 tokens for an 18-decimal VFT, 1 000 tokens for a 0-decimal
   VFT. The pool program is not affected: VARA is always D12 and `MIN_STAKE = 1e10` is documented as
   "0.01 VARA (12 decimals)".
2. The receipt token's `decimals` is whatever the deployer passes; nothing compares it with
   `underlying.decimals()`. Shares are minted 1:1 with assets at rate 1.0 (`shares_for` =
   `assets * 1e18 / base_rate`), so shares *always* carry the underlying's precision regardless of the
   metadata. If `decimals` ≠ the underlying's, every wallet/explorer renders kUSDC balances with the wrong
   scale while the on-chain arithmetic stays internally consistent.

Dimensionally the arithmetic is sound because both sides of every comparison are the underlying's base
unit and the rate is decimals-neutral (`D6{asset} * D18 / D6{share}` cancels). The finding is about the
unchecked assumption, not the algebra.

Concrete numbers for the deployed configuration (D6 tokens): `MIN_DEPOSIT` = 0.001 USDC, consistent with
the doc comment, and the "share rounding can never produce zero" claim holds for any `base_rate` below
`1_000 * 1e18` (shares = `1_000 * 1e18 / base_rate` ≥ 1). For a hypothetical 18-decimal underlying the
minimum becomes 1e-15 tokens: the claim still holds, but the minimum is meaningless as a dust guard.

## Impact

None for the current deployment (`deploy.ts` passes `6` to both the demo token and the vault). Latent risk
only if the vault code is reused over a token with different decimals, or if a deployer passes a wrong
`decimals` argument: mis-rendered receipt balances and an effectively absent minimum-deposit guard.

## Recommendation

Either pin the assumption or derive it:

- Pin: document in the module header that the vault is for D6 underlyings only, and rename the constant to
  make the scale explicit, e.g. `MIN_DEPOSIT_D6`.
- Derive: at construction (or lazily on first deposit, since the constructor is synchronous) read
  `underlying.decimals()` and store `min_deposit = 10u128.pow(decimals as u32) / 1_000` (0.001 tokens), and
  reject or overwrite a `decimals` argument that does not match the underlying. `deploy.ts` can also assert
  `info.decimals === 6` alongside its existing `info.underlying` check at line 163.
