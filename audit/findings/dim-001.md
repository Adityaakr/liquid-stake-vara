# DIM-001: Rewards tranche is sized with the unclamped vesting period, so the first APY can be off by the clamp ratio

**Severity:** LOW
**Type:** scale_factor_mismatch (same unit `{s}`, two different magnitudes for the "same" quantity)
**Location:** `/Users/adityakrx/liquid-stake/scripts/deploy.ts:39,53-54,104,134,143`
**On-chain counterpart:** `/Users/adityakrx/liquid-stake/programs/vara-pool/app/src/lib.rs:201` and `/Users/adityakrx/liquid-stake/programs/vault/app/src/lib.rs:222` (`vesting_period_secs.clamp(MIN_VESTING_SECS, MAX_VESTING_SECS)`)

## Code

```ts
// scripts/deploy.ts
const VESTING_SECS = Number(args.vesting ?? 7 * 86_400);                       // {s}, NOT clamped
const tranche = (principal: bigint, apyBps: bigint) =>
  (principal * apyBps * BigInt(VESTING_SECS)) / (10_000n * YEAR_SECS);         // {asset} * D4{1/yr} * {s} / (D4 * {s/yr}) = {asset}
...
pool.newCtorFromCode(poolWasm, ..., UNBOND_SECS, VESTING_SECS, startRate(...)) // program receives VESTING_SECS
```

```rust
// programs/vara-pool/app/src/lib.rs (vault is identical)
vesting_period_ms: vesting_period_secs.clamp(MIN_VESTING_SECS, MAX_VESTING_SECS).saturating_mul(1000),
```

## Analysis

The tranche formula is dimensionally correct: `{asset} * D4{1/yr} * {s} / (D4 * {s/yr}) = {asset}`, and
the on-chain `apy_bps` (`vest_amount * YEAR_MS * BPS / (span * distributable)`) reproduces exactly `apyBps`
when `span == VESTING_SECS * 1000`. That identity is what the comment on line 49-52 promises
("seeding with this amount shows exactly the target APY until the tranche runs out").

The identity breaks whenever the value the script uses for `VESTING_SECS` differs from the value the
program actually uses. The programs clamp `vesting_period_secs` into `[3_600, 31_536_000]` silently;
the script does not, and it uses the raw value both for the tranche size and for the constructor argument.

Concrete numbers (`--stake 1000 --vesting 60`, POOL_APY_BPS = 3500):

| | Script assumes | Program uses |
|-|----------------|--------------|
| vesting span | 60 s | 3 600 s (clamped) |
| tranche | `1e15 * 3500 * 60 / (1e4 * 31_536_000)` = 666 million planck = 0.000666 VARA | same amount |
| release rate | 0.000666 VARA / 60 s | 0.000666 VARA / 3 600 s |
| `apy_bps` reported | 3 500 (35 %) expected | `6.66e8 * 3.1536e10 * 1e4 / (3.6e6 * 1e15)` = **58 bps (0.58 %)** |

The other direction: `--vesting 63072000` (2 years) is clamped to 1 year, so the tranche vests twice as fast
and the pool reports **7 000 bps** instead of 3 500.

Note that `set_config` on chain *rejects* an out-of-range vesting period (`BadConfig`), while the constructor
silently clamps, so this is only reachable at deploy time. The rest of the vesting time-unit chain
(`* 1000` at the boundary, `vest_end_ms - vest_start_ms` in ms, `YEAR_SECS * 1000` in ms) is consistent.

## Impact

Deploy-time only, and only when `--vesting` is outside `[3600, 31536000]`. The default (7 days) is inside
the range. When triggered, the published APY on the freshly deployed pools is wrong by the factor
`VESTING_SECS / clamp(VESTING_SECS)` and the deploy log ("vesting over 60s") disagrees with the program's
`vesting_period_secs`. No funds are at risk; the mis-sized tranche still vests in full.

## Recommendation

Clamp once, in the script, with the same bounds the programs use, and derive both the tranche and the
constructor argument from the clamped value (or refuse out-of-range input):

```ts
const MIN_VESTING_SECS = 3_600, MAX_VESTING_SECS = 365 * 86_400;               // mirror the programs
const requested = Number(args.vesting ?? 7 * 86_400);
const VESTING_SECS = Math.min(MAX_VESTING_SECS, Math.max(MIN_VESTING_SECS, requested));
if (VESTING_SECS !== requested) console.warn(`--vesting ${requested}s is outside the programs' range; using ${VESTING_SECS}s`);
```

Optionally assert after deploy that `poolInfo.vesting_period_secs === VESTING_SECS` before funding the tranche.
